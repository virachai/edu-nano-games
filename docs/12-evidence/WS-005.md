## Regression Found & Fixed (2026-09-19, post-handoff)

A reviewer re-run on a machine where `bash` on `PATH` resolves to the WSL launcher
(`C:\Windows\System32\bash.exe`, which has `flock` from util-linux available)
surfaced a failure in `tests/agent-runner-validation.test.js`:

```text
not ok 8 - agent-runner.sh prevents concurrent executions via locking
Expected "actual" to be strictly unequal to: 0
actual: 0
```

**Root cause:** the test simulated "another runner is active" by only pre-creating
the `mkdir`-based fallback lock directory (`.runner.lock.d`). `scripts/agent-runner.sh`
picks its locking strategy at runtime (`flock` if present on `PATH`, else `mkdir`
fallback). When the resolved `bash` has `flock` available, the script takes the
`flock` branch, never inspects the pre-created `.runner.lock.d`, acquires a fresh
uncontended `flock`, and exits 0 — the test's simulated lock state didn't match the
strategy the script actually chose. This was a test-design flaw coupling the
assertion to one specific fallback branch, not a broken locking implementation —
`scripts/agent-runner.sh` itself required no changes.

**Fix:** the test was rewritten to launch a real first `agent-runner.sh` invocation
asynchronously (holding whichever lock strategy the environment selects for ~3s),
wait for it to log `START`, then run a second invocation synchronously and assert
it fails with a non-zero exit and the `another agent runner is already active`
message. This validates the actual mutual-exclusion behavior regardless of which
locking strategy is active. Re-verified passing twice in a row locally (see
Verification Results below) to rule out timing flakiness.

Status remains `EVIDENCE_COMPLETE` throughout — not reset to `READY`, not advanced
to `DONE` — per repository protocol (only DWB105 review may set `DONE`).

- Task discovery helper inspects `docs/BACKLOG.md` table structure and dependency completeness; semantic validation of task preconditions remains within agent execution.
