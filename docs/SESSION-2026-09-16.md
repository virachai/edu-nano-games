# Session Summary — 2026-09-16

## Purpose
Capture the working agreement and architecture discussed in this session for using GPT-5.6 Luna together with local AI agents in the `edu-nano-games` workspace.

## Core Working Model

The intended workflow is:

```text
Human / Product Direction
        ↓
GPT-5.6 Luna
(Architect / Planner / Reviewer)
        ↓
Workspace Docs
(BACKLOG + TASKS + RULES + ACCEPTANCE)
        ↓
Local AI Agents
(Gemini / other agents)
        ↓
Code / Artifacts
        ↓
Tests / Render / Evidence
        ↓
GPT Review
        ↓
Fix / Verify / Done
```

The goal is to make the workspace documents the contract between the planning/review layer and execution agents.

## Role Separation

### GPT-5.6 Luna
- Analyze requirements and project state.
- Design architecture and execution plans.
- Break milestones into executable tasks.
- Create and maintain agent-facing documentation.
- Review implementation, tests, artifacts, and evidence.
- Identify inconsistencies, risks, and missing acceptance criteria.
- Generate follow-up/fix tasks when verification fails.

### Local Agents
- Read the workspace documentation before acting.
- Execute READY tasks.
- Modify source files and artifacts within documented constraints.
- Run required tests/build/render commands.
- Record completion evidence.
- Do not declare work complete merely because code compiles.

### Human
- Own product direction and final decisions.
- Approve architectural or scope changes when needed.
- Run local agents and provide/review results as appropriate.

### Source of Truth
Repository files and explicit project evidence take precedence over model assumptions or conversation memory.

## Proposed Documentation Protocol

Recommended workspace structure:

```text
docs/
├── INDEX.md
├── FLOW.md
├── ARCHITECTURE.md
├── BACKLOG.md
├── AGENT_RULES.md
├── tasks/
│   ├── MM-001.1.md
│   ├── MM-001.2.md
│   └── ...
└── evidence/
    ├── MM-001.1.md
    ├── MM-001.2.md
    └── ...
```

### BACKLOG.md
Should contain actionable task state, dependencies, priorities, and readiness rather than vague TODOs.

### tasks/*.md
Each task should be an executable contract containing at least:
- Objective
- Agent instructions
- Required files/context
- Constraints
- Dependencies
- Acceptance criteria
- Required tests/commands
- Required completion evidence

### AGENT_RULES.md
Should define common execution rules for all local agents, including:
- Read relevant docs before modifying code.
- Preserve documented interfaces/contracts.
- Do not silently expand scope.
- Run required verification.
- Report changed files and evidence.
- Distinguish IMPLEMENTED from VERIFIED/DONE.

### evidence/*.md
Should preserve concrete proof of completion, such as:
- Commands executed
- Test results
- Render results
- Generated artifact paths
- Relevant verification notes

## Suggested Task Lifecycle

```text
PLANNED
  ↓
READY
  ↓
IN_PROGRESS
  ↓
IMPLEMENTED
  ↓
VERIFIED
  ↓
EVIDENCE_COMPLETE
  ↓
DONE
```

`DONE` requires the task's acceptance criteria and evidence requirements to be satisfied.

## Agent Invocation Concept

A local agent can be given a short stable command because the detailed contract lives in the workspace:

```bash
gemini -m gemini-3.5-flash-lite \
  -p "อ่านไฟล์ backlog แล้วทำ task ที่พร้อมทำให้เสร็จ โดยทำตาม instruction ในเอกสารอย่างเคร่งครัด ตรวจ tests และ update evidence ด้วย" \
  2>/dev/null
```

The exact command/model may change; the important principle is that the agent reads the repository documentation rather than receiving the entire task specification through an ad-hoc prompt.

## Design Principle

Do not optimize for making the human write longer prompts. Optimize for making the repository self-describing and executable by agents.

The preferred loop is:

```text
GPT creates/updates task docs
        ↓
Agent executes
        ↓
Agent produces evidence
        ↓
GPT reviews
        ↓
Fix task if necessary
        ↓
Agent executes again
        ↓
Verified
```
